# 《水织 / WaterWeave》设计稿

> 类型：无压力线路式逻辑解谜
> 平台：单 HTML 文件，浏览器即玩，零后端
> 场景：Garena GMAP 管培生申请展示作品
> 日期：2026-10-19

---

## 一、一句话定义

**在网格上开渠成环，让水路通达隋唐洛阳的水系；规则是硬的，灯火是软的。**

玩家扮演**河渠吏**，在方格之间开凿水道。水道必须满足数字约束、连成一条闭合水路。当水路完成，被它流过的村落、码头、粮仓会依次亮起灯火，一艘漕船沿水路巡行一圈——玩家不是在"解题得分"，是在**给故乡点灯**。

英文名 **WaterWeave**：水为线，织城成锦。

---

## 二、核心机制

### 2.1 硬约束（规则层，不妥协）

在网格的**边**上开渠。每条边有三种状态：

- **空白**（未决定）
- **开渠**（水道）
- **标记**（划叉，确认不开）

满足以下五条即为通关：

1. **数字约束**：带数字 N 的格子，其四周**恰好**有 N 条边开渠（N ∈ {0, 1, 2, 3}）
2. **单一回路**：所有开渠的边**恰好**构成**一条**闭合回路（不能是两条，也不能有断路）
3. **格点度数**：每个格点上相连的渠数为 **0 或 2**（不允许出现 1、3、4，即不允许断头与分叉）
4. **无孤立渠**：不允许存在不属于该闭合回路的渠段
5. **闸口约束（进阶关）**：标记为闸口的格点，回路**必须**经过

> 设计注：三态标记是数回解题手感的必需品，不能简化为两态。

### 2.2 软层（表现层，第一处修正）

**关键修正：聚落不以"目标"形式出现，只以"结果"形式出现。**

- 聚落（村 / 码头 / 粮仓 / 桥 / 寺院）布置在**格点**上
- 回路的每个格点恰好连接两条渠 —— 该格点即"水路流经之处"
- **回路流经该格点 → 聚落亮灯**

因此：

- 数字约束**决定**唯一回路
- 回路**决定**哪些聚落亮灯
- 玩家**不需要为聚落做任何取舍**

**从"为了点亮节点去连线"改为"通航之后，才发现水路穿过了这么多人家"。** 繁荣是被发现的，不是被优化的。

这一段是设计稿的核心决策，它同时解决了"机制冲突"和"分数焦虑"两个问题。

## 三、奖励系统：无分数设计（第二处修正）

**通关不给分，只给三件事，按顺序触发：**

| 顺序 | 内容 | 时长 |
|---|---|---|
| 1 | **灯火**：回路经过的聚落按路径顺序依次亮灯 | 约 1.2s |
| 2 | **巡船**：一艘漕船沿回路匀速巡行一圈，尾迹是渐隐的银蓝 | 约 3s |
| 3 | **一纸注记**：一屏史实小卡，放映本关对应河段的真实历史 | 停留至玩家点击 |

**史实注记示例**：

- 含嘉仓：已探出粮窖 400 余座，其中一窖出土铭砖记载存粟约 50 万斤
- 天津桥：隋唐洛阳城跨洛水之桥，隋时以铁锁连舟为浮桥
- 回洛仓：隋大业年间置，为洛阳城外重要粮储

**进度表达**：不用分数条，用**「漕运图鉴」**——一张洛阳水系总览图，已通航的河段在图鉴上点亮。进度感来自"地图被点亮"，而不是数字上涨。

---

## 四、入门设计：把门槛压到 20 秒（第三处修正）

数回在中国不普及，这是本作最大的可玩性风险。三重对策：

### 4.1 第 0 关即教学关

- 网格 **3×3**，只放 **2 个数字**（一个 0、一个 2）
- 目标：**20 秒内可解出**
- 首屏进入即教学关，没有欢迎页、没有大段文字

### 4.2 规则用动效讲，不用文字

三屏自动播放，每屏约 3 秒：

| 屏 | 画面 | 传达 |
|---|---|---|
| 1 | 一格亮起数字「2」，其四条边中两条亮起 | 数字 = 四周渠数 |
| 2 | 渠连成一个圈，接缝处闭合发光 | 水路必须成环 |
| 3 | 圈流过一个村落，村落亮起灯火 | 通航即点亮人家 |

### 4.3 术语全部翻译成漕运语言

| 抽象术语 | 游戏内用词 |
|---|---|
| 边 | 渠 |
| 开渠 | 开水路 |
| 顶点 | 水口 |
| 格点度数 | 水口分叉 |
| 闭合回路 | 水路成环 |
| 关键约束点 | 闸口 |

全程**不出现**"边""顶点""回路""算法"等词汇。

## 五、关卡结构

8 关 + 回廊（重玩已通关卡）。全部手工设计，逐关验证唯一解。

| 关 | 网格 | 数字数 | 新增机制 | 地图对应 |
|---|---|---|---|---|
| 0 | 3×3 | 2 | 教学 | —— |
| 1 | 4×4 | 4 | 无 | 瀍水小渠 |
| 2 | 5×5 | 6 | 引入数字 0 | 洛水南岸 |
| 3 | 5×5 | 7 | 引入数字 3 | 伊水渡口 |
| 4 | 6×6 | 8 | **闸口 ×1** | 天津桥 |
| 5 | 6×6 | 9 | 闸口 ×2 | 回洛仓 |
| 6 | 7×7 | 10 | 无 | 含嘉仓 |
| 7 | 7×7 | 11 | 闸口 ×3 + 河道形轮廓（L 形） | 洛口仓 |
| 回廊 | 已通关卡 | —— | 重玩已通关卡，点亮不同聚落 | 全图拼合 |

难度曲线原则：**新机制只在一关引入，下一关消化，再下一关叠加。**

## 六、视觉规范

### 6.1 构图

- 俯视 2.5D，等距微倾斜约 **15°**
- 网格为**夯土色方格地**，格线极细（1px，`#3A4750`）
- 聚落以**建筑剪影**呈现，不做细节

### 6.2 色板（暮色为主方案）

| 用途 | 色值 | 说明 |
|---|---|---|
| 底色（暮色） | `#2A3440` | 保留残余天光，建筑剪影可读 |
| 底色（通航时切深夜） | `#16202B` | 情绪高点 |
| 地格 | `#33414E` | |
| 水面 / 渠 | `#8FA6B8` | 银蓝，**饱和度锁定 ≤ 30%** |
| 灯火 | `#F2C879` | 暖黄，**仅出现在聚落** |
| 建筑剪影 | `#0E161E` | 近乎黑的青，只留轮廓 |
| 文字 / 注记 | `#EDE6D6` | 米白 |

**克制原则**：灯火只在聚落处发光（半径 12–20px 柔光）；水面保持接近灰蓝，避免做成"夜景灯光秀"。

### 6.3 动效

| 动作 | 表现 |
|---|---|
| 开渠 | 0.12s 从点击端向另一端"生长" |
| 亮灯 | 0.15s 柔光绽放 |
| 巡船 | 沿回路匀速，尾迹渐隐银蓝 |
| 通航 | 底色从暮色平滑过渡到深夜 |

**缓动曲线统一用 ease-out，禁用弹跳与回弹——全作保持"静"。**

## 七、技术架构

### 7.1 单文件结构

- HTML 骨架 + CSS 变量（色板集中定义）+ 一份内嵌 JSON 关卡数据 + Canvas 2D 渲染 + DOM 覆盖层（文字、注记卡片）

### 7.2 数据模型

```
level: {
  cols, rows,
  numbers: Map<"r,c", 0|1|2|3>,
  gates:   [{r, c}],           // 闸口格点，进阶关使用
  settlements: [{r, c, type, name}]
}
state: {
  edges: Map<"r,c,dir", 0|1|2>  // 0 空白 / 1 开渠 / 2 标记
}
```

### 7.3 交互

点击一条边 → 循环切换 **空白 → 开渠 → 标记 → 空白**。
支持拖拽连续绘制。

### 7.4 校验器（每步实时运行）

1. 每个数字格四周的渠数是否等于其数字（不等则该数字变色提示，不判负）
2. 每个格点的渠度数是否 ∈ {0, 2}
3. 所有渠是否构成**单一**闭合回路（并查集判连通 + 遍历计数判环的个数）
4. 闸口是否被经过

**只提示，不判负**——不打断思考节奏。

### 7.5 求解器（仅开发期）

位运算 DFS + 剪枝，用途：**逐关验证唯一解**。

**明确不追求程序化生成**——宁可手工设计 8 关并逐关校验。

### 7.6 渲染

Canvas 2D 负责地面、渠、光晕、剪影、巡船；DOM 覆盖层负责文字与注记卡片。

## 八、范围界定（不做的事）

- 不做多人联机、不做语音
- 不做云存档、不做账号
- 不做程序化关卡生成（手工 8 关）
- 不做 3D、不做物理模拟
- 不做音效库（可选：一条环境水声循环）

## 九、风险与对策

| 风险 | 级别 | 对策 |
|---|---|---|
| 数回入门门槛高 | 高 | 3×3 教学关 + 动效图解 + 漕运语言翻译 |
| 关卡唯一解无法保证 | 高 | 开发期写求解器逐关验证；手工设计 |
| 夜景审美滑向俗艳 | 中 | 灯火只在聚落；水面饱和度锁定 ≤ 30% |
| 无分数导致动力不足 | 中 | 用「漕运图鉴」点亮点阵替代分数；每关尾一屏史实注记 |
| 面试官耐心约 90 秒 | 中 | 首屏即教学关；20 秒内可解出即视为达标 |

## 十、面试叙事

**一句话**：

> 我把「数回」——一种与数独齐名的纸笔逻辑谜题——做成了隋唐大运河洛阳段的漕运水系。规则是硬的，灯火是软的；玩家不是在解题，是在给故乡点灯。

**这一作对应 GMAP 的素质**：

| GMAP 考察项 | 本作的证据 |
|---|---|
| 热爱游戏 | 数回是核心玩家才知道的解谜门类；审美对标 WILDOKU |
| 天赋与敏捷 | 机制选型经过多轮否定与收敛，最终落在一个已被验证的解谜范式上 |
| 魄力与韧性 | 从概念到可玩 Demo 的完整落地 |
| AI 创新 | AI 辅助关卡验证与美术实现，规则设计由人完成 |
| 文化表达 | 洛阳在水系与漕运上的历史锚点（含嘉仓、天津桥、回洛仓、洛口仓） |

**必须准备的答辩点**：若被问"为什么不用数独"，回答——

> 数独是**格内填充**、靠排除法；数回是**边线构图**、靠回路唯一性推导。思考系统不同，视觉呈现也不同。而且数独已经有一个 WILDOKU 做过了，我不想做第二个。

## 十一、验收标准

作品完成需同时满足：

1. 第 0 关可被首次接触者 **20 秒内**解出
2. 8 关全部通过求解器验证**唯一解**
3. 通航后灯火级联 + 巡船动画完整播放
4. 全作无分数、无失败判定
5. 单 HTML 文件交付，双击即玩，无外部依赖
6. 30 秒内可录出"解出 → 灯火亮起 → 巡船"的完整演示视频
